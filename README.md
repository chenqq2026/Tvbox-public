TVBox / FongMi 影视 / OK影视 的配置源。**每天北京时间 05:17 由 GitHub Actions 自动重建**，不需要手动维护。

### 主地址（单仓，推荐）

```
https://ghfast.top/https://raw.githubusercontent.com/chenqq2026/Tvbox-public/main/config_all.json
```

### 精简版地址（可选，与主地址并行对比用）

```
https://ghfast.top/https://raw.githubusercontent.com/chenqq2026/Tvbox-public/main/config_lite.json
```

只保留**实测能搜到片的 10 个直连站 + 9 个可用解析器**，直播 / EPG / jar / 规则与主配置逐项相同。
**主配置一个字没改**，两个地址随时在遥控器里切换、互不影响。对比数据和门槛见第五节「精简版和主配置该用哪个」。

### 备用加速通道（内容完全相同，只换开头域名）

`ghfast.top` 抽风时，把地址开头的 `https://ghfast.top/` 换成下表任意一个，
**后面整段路径一个字都不要改**：

| 通道 | 主配置 | 备用聚合 | 直播 m3u | jar | 备注 |
|---|---|---|---|---|---|
| `ghfast.top` | 🟢 1.0s | 🟢 3.0s | 🟢 2.3s | 🟢 1.9s | **首选**，jar 最快 |
| `gh-proxy.com` | 🟢 0.8s | 🟢 2.6s | 🟢 3.9s | 🟢 3.2s | 次选，与首选基本持平 |
| `ghproxy.cc` | 🟢 2.6s | 🟢 4.5s | 🟢 5.8s | 🟢 4.1s | 备选 |
| `ghproxy.net` | 🟢 1.3s | 🟢 2.0s | 🟢 5.8s | 🟡 59.4s | 拉配置行，拉 jar 很慢 |
| `cdn.jsdelivr.net/gh/chenqq2026/Tvbox-public@main/` | 🟢 2.4s | 🟢 3.0s | 🔴 超时 | 🔴 失败 | 最后备选，见下方警告 |

以 `gh-proxy.com` 为例（备用聚合同理）：

```
https://gh-proxy.com/https://raw.githubusercontent.com/chenqq2026/Tvbox-public/main/config_all.json
https://gh-proxy.com/https://raw.githubusercontent.com/chenqq2026/Tvbox-public/main/spare_juhe.json
```

> ⚠️ **jsDelivr 只适合应急**：① 路径格式不同，是 `cdn.jsdelivr.net/gh/用户/仓库@main/文件`，
> 没有 `https://raw.githubusercontent.com/` 这一段；② **只提供配置，直播清单和 jar 都拉不到**；
> ③ CDN 缓存 12 小时 + 客户端缓存 7 天，配置每天更新，用它会出现「明明更新了盒子上还是旧的」，
> 很容易误判成自动更新失效。

> 实测时间 2026-11-05 11:24（11-04 也测过一轮）。这类公益代理负载波动大，
> 前一天 ghfast.top 拉主配置还要 7.0s，今天就降到 1.0s——数值只作相对参考，
> 排名也会轮换。真正影响体验的是 jar 下载速度（TVBox 启动/更新时拉 1.84MB），
> 哪个通道 jar 快就用哪个当主。

直播是**双源合并**：主源 `vbskycn/iptv`（地方台全，但已不含 CCTV-1/2/3/4/6/7/9/10/11/14），
补源 `Guovin/iptv-api`（央视 1–17 每台多线路）。少任何一个都会缺台——这是实测出来的。

## 三、自动更新每天做什么

`.github/workflows/daily-update.yml`，每天 UTC 21:17（北京 05:17，qist bot 更新之后）：

1. **拉 qist 最新 `jsm.json`** → 修相对路径 → `jsm_fixed.json`
2. **拉 `spider.jar`** → 校验（ZIP 头 + 体积 + 与 qist 声明的 md5 一致）→ 镜像到 `jar/spider.jar`
3. **直播**：主源 vbskycn + 补源 iptv-api（只取央视/卫视）→ 逐频道请求验证（失败补测一轮）→ 逐条下载分片实测带宽 → 央视/卫视留 3 条、其余留 2 条 → 低于 500kbps 标「（慢）」→ 按三级证据继承上一版的旧线路（详见下方防抖保险）
4. **直连 CMS 探活**：8 个自持站当天返回不了片单的临时剔除
5. **解析器**：实测排序，把挂掉的排到后面
6. **EPG**：探测候选源，选可用的写入配置
7. **备用聚合镜像**：拉 `Lightconer/tvbox-ysc-config` 的单仓聚合 → 校验站数 → 剔掉它夹带的假直播源 → 连它的 spider jar 一起镜像 → 写 `spare_juhe.json`（任何一步失败都保留旧文件，不覆盖）
8. **精简版全自动维护**：`lite_auto.py` 在 CI 每天实测 18 站 × 8 关键词 + 8 个留出集词 + 全部解析器 → 双源与门衰减演化名单（连续 3 天 0 命中才淘汰 / 连续 2 天达标才加回 / 本机判死站永不自动加回）→ 从最新主配置派生 `config_lite.json`。整体异常或任一门槛不过就**零写入**。不再需要手动刷新证据，也不会冻结
9. **写 `health.json`** + 有变化才提交

`.github/workflows/weekly-prune.yml`，每周一 05:47：对备用配置做站点健康巡检，
用 DNS 判定识别「域名已不存在」和「被 DNS 污染」的站点。**默认只报告不写文件**——
老 gao 配置里大量 `csp_` 内置源无法提取主域名，自动写入会把它退回未剔除版本。

**四道防抖保险**（防止一次网络抖动把成品写坏）：
- 拿不到合法 jar（体积/ZIP 头/md5 校验不过）→ 直接中止，保留线上旧版本
- **线路继承（三级证据，2026-11-06 重做）**：CI 跑在海外机房，对国内地方台系统性不可达——曾出现频道数连续三天 347→332→322，而本机复验被剔除的 14 个台 14/14 全部能播。旧逻辑拿同一个 CI 探测器去「复验」它自己判死的线路，等于用坏尺子量两次。现在：
  1. 上游当前清单里**仍有**这条 url → 直接继承，不再要求 CI 复验通过（上游每天维护清单，它留着就是最强存活信号）
  2. 上游已撤、但**曾实测下载过分片**（`live_speed.json` 里 kbps>0）→ 保留，真下过视频数据比一次超时可靠
  3. 上游已撤且从没测出过速度 → 复验 + `live_miss.json` 记连续失败天数，30 天后才淘汰
  
  也就是说，淘汰只发生在「上游撤了且从来没有验证证据」的线路上。`health.json` 里 `carry_alive / carry_gone / carry_kept / carry_expired` 可以逐项核对。
- **来源可信度判定**：上游拉到了、验证通过率 ≥ 50% → 条数变少按「上游真实精简」放行；只有来源可疑时才拦下，且低于 100 条绝不覆盖
- CCTV1/2/5/13、主要卫视若被漏判 → 从上游补一条进去，核心频道永不为空

> 这两种网络环境都不完美：Actions 在海外机房，到国内 IPTV 源的可达性和带宽都低于家宽；
> 本机则常被代理挡住大流量分片。所以 `health.json` 里的 `median_kbps` 只作**相对**参考
> （用来排序、标「（慢）」），不代表你家里的实际速度。同理，`live.measured_now` 和
> `inherited_kbps` 会告诉你这次有多少是实测、多少是沿用上次结果。

## 五、常见问题

**Q：提示「解析配置失败」**
1. 先确认用的是 `config_all.json`（单仓）。`config.json` 是多仓格式，部分壳不认。
2. 再重试 2 次——gh-proxy 偶发瞬断，TVBox 拉取那一刻断了就会报这个。
3. 还不行换备用通道，把开头的 `gh-proxy.com` 换成 `ghfast.top` / `ghproxy.cc` / `ghproxy.net`
   任意一个，后面路径不动（见「一、导入地址」的通道表）。

**Q：能进配置，但点开站点没反应 / 一直转圈**
大概率是 spider 引擎没加载。到 `health.json` 看 `jar.declared_match` 是否为 `true`；
再看播放器设置里的「spider 参数」是否为空。本仓库的 spider 指向自己仓库的 jar，不依赖 qist。
如果只有部分站这样，那是站点本身挂了（spider 站的生命周期普遍只有几个月）。

**Q：某个频道很卡**
看 `live_verified.m3u` 里该频道名有没有「（慢）」标记，或者查 `live_speed.json` 里它的 kbps。
同一频道通常有 2 条线路（`CCTV1`、`CCTV1▪2`），换另一条试。

**Q：点播看着看着卡（缓冲转圈）**

2026-11-06 本机国内网络实测，40 条真实视频分片全部测通：带宽 p10 590 / 中位 **872** /
p90 1530 kbps，**98% 低于 2000 kbps**。1080p HLS 通常要 2000–4000 kbps，
所以主因是**下载速度喂不饱码率**，不是配置写错。换站点也没用：131 条播放地址
只来自 6 个源站主域，前 2 个占 69%，165 个站点大多是同一批 CDN 的不同门面。

立刻能缓解的（在壳里设，不用改仓库）：
1. **清晰度降到 720p** —— 当前带宽下最立竿见影
2. 播放器缓冲调大 / 换 EXO 内核
3. 手动只勾 `health.json → parses` 里实测可用的解析器，别让壳轮询死接口

**为什么不直接「加更多不同 CDN 的源」**：试过了。`scripts/expand_cdn.py` 从
王二小 / 小马 / 小盒子 / Lightconer / rtian001 / 本仓镜像共 6 个上游提取到 31 个直连 CMS，
落在现有主域之外的「新」主域只有 7 个，其中 6 个本机 DNS 解析失败；两轮独立采样
带宽中位 790 / 899 kbps，和 872 的基线**没有显著差异**。换上游换不掉后端瓶颈，
这是采集站生态的结构性限制，不是找得不够多。

**守门机制**（`scripts/expand_cdn.py`，只在本机跑，不进 CI）：
CI 在海外机房，测国内 CDN 会系统性偏低——直播线路误杀已经踩过这个坑，所以
带宽判定绝不放进 Actions，CI 只转述已验证结果。工具内置 4 条**与门**门槛：

| 门槛 | 要求 |
|---|---|
| 新主域 | ≥3 个且测通 ≥3 个 |
| 两轮独立采样中位 | 均 ≥ 基线 2 倍 |
| 两轮一致性 | 差异 < 30% |
| 最快线路 | 至少 1 条 ≥ 3000 kbps |

任一不过就**零写入**，主配置保持原样；全过才生成 `vod_fast_sites.json`，
每日更新在 7 天内自动合入并置顶。想重新探测：

```
python scripts/expand_cdn.py
```

`health.json` 的 `vod_cdn` 段转述最近一次报告（是否达标、新主域数、前 2 主域占比、
加速站是否生效）。截至 2026-11-06 结论为**未达标、零写入**。

**Q：精简版和主配置该用哪个**

**两个都留着，建议先用精简版跑一周**——主配置地址一个字没改，随时能在遥控器里切回去。
精简版治的是「站点太多、搜索并发慢、死站点开就崩、解析器轮询一圈超时」，
**治不了播放中缓冲**（那是源站带宽，见上面那条）。

2026-11-06 本机国内网络实测：

| 项 | 主配置 `config_all.json` | 精简版 `config_lite.json` |
|---|---|---|
| 站点 | 165（22 直连 + 142 spider + 1） | **10**（全部直连） |
| 解析器 | 27（实测可用 9） | **9**（全部可用，按耗时排序） |
| 直播 / EPG / jar / flags / rules / ads | 完全相同 | 完全相同 |
| 8 个探测关键词覆盖 | 每词 9–10 站 | 每词 9–10 站 |
| 8 个**全新**留出集关键词 | 8/8 覆盖 | **8/8 覆盖**，每词 9–10 站 |

怎么选出来的：对 18 个去重直连 CMS 各搜 8 个关键词，**能不能搜到片**才是判据。
原来的 `cms_alive()` 只看响应头有没有 `"code"`/`"list"`，把 8 个纯摆设站全放过了——
`health.json` 当天报 `cms_dead_today: []`（一个没剔），实测却有 8 个站 0/8 命中。
**存活性 ≠ 可用性**，这是本次重做修掉的机制漏洞。

10 个站 ≥7/8 命中，8 个站 0/8 命中；再用 8 个探测时从未用过的留出集词复验：
保留站平均命中 **7.80/8**，淘汰站 **0.00/8**，不是过拟合。
留出集复验已内置进工具，以后每次刷新证据都会自动跑。

> **诚实边界**：主配置 `config_all.json` 的 `cms_alive()` 保持原样，没有收紧。
> 它管着 165 个站，且主配置的直播继承链路已被 CI 误杀验证过，直接改风险大。
> 搜索实测的淘汰结果目前**只作用于精简版**，并作为 `health.json → lite.zero_hit_sites`
> 每天留痕。等你确认精简版够用，再决定要不要把同一判据推广到主配置。
> （点播采集站的 CI 可达性已由探路证伪旧顾虑，详见下方「全自动维护」。）

守门门槛（**与门**，任一不过就配置零写入、保留旧版）：

| 门槛 | 要求 |
|---|---|
| 网络整体正常 | 请求成功率 ≥50% 且至少一个站出片（防代理瞬断） |
| 能出片站点 | ≥5 个 |
| 探测词覆盖 | 8 个词每个至少 2 个达标站能出片 |
| 留出集覆盖 | 8 个新词每个至少 2 个达标站能出片 |
| 可用解析器 | ≥3 个 |
| 站点骤降防抖 | 达标站骤降 >50% 需连续两次观测确认 |

### 全自动维护（2026-11-06 探路后升级，零手动）

原先的顾虑是「CI 海外机房测国内站会误判」。先在真实 Actions 里跑了一次探路
（`ci_probe_result.json`），结果**推翻了这个担心**：

| 指标 | CI 实测 | 判定 |
|---|---|---|
| 请求成功率 | 120/144 = **83.3%** | 🟢 高于本机 72.2% |
| TTFB 中位 | **233ms** | 🟢 比本机快 |
| 本机 10 个活站召回 | **100%，零误杀** | 🟢 |
| CI 额外判活的站 | **2 个**（非凡 8/8、尤酷 7/8，本机均 0/8） | 🔴 **误纳** |

真正的风险不是「把活站判死」，而是「**把国内用不了的站判活**」——海外可达 ≠ 你家里能用。
所以落地的是**双源与门**，不是让 CI 直接接管名单：

| 规则 | 内容 |
|---|---|
| 本机基线 | 本机 `probe` 结果是硬基线；7 天内名单锁定，CI 只累计衰减计数并每天重建配置 |
| 7 天后 | CI 接管演化：连续 3 天 0 命中才淘汰、连续 2 天达标才加回 |
| `locked_out` | 本机明确判死的站**永不由 CI 自动加回**（专门防上面那 2 个误纳） |
| 解析器 | CI 每天复验，连续 3 天判死才剔除；不自动新增 |
| 作废 | 单日成功率 <50% 或全站 0 命中 → 观测作废；活站批量判死 >50% 也作废 |
| 零写入 | 任一门槛不过 → `lite_state.json` / `lite_probe.json` / `config_lite.json` 全不写 |

> **这不推翻直播的结论**：直播 IPTV 地方台受地域/运营商限制，CI 系统性不可达
> （347→332→322，本机复验 14/14 可播）；点播采集站是公网 CDN。两者性质不同，结论不同不矛盾。

想用自己网络重设基线（会覆盖 CI 的名单演化结果）：

```
python scripts/build_lite.py
```

`health.json → lite` 显示证据时间、门槛结论、0 命中站清单、留出集覆盖、今日是否重建成功；
`lite.auto` 显示来源、本机基线是否生效、锁定站数、被拦截的 CI 误纳数、今日名单变化次数。

> 精简版里有两个 `http://` 明文站（电影天堂、建安）。部分 Android 壳默认禁止明文流量，
> 表现为这两站点开无数据，其余 8 个 https 站不受影响。要彻底干净可手动删掉这两条。

**Q：没有节目单（EPG）**
先看 `health.json` 的 `epg` 字段是不是「无可用源」。公共 EPG 服务生命周期很短，
四个候选（112114 / fanmingming / epg.pw / 51zmt）目前基本全挂，现用的是 `epg.cdn.loc.cc`。
彻底解决只能自建（iptv-api 支持输出 EPG）。

**Q：为什么站点列表比网上那些「几千个站」的配置少这么多**
那些配置里大部分站早就死了，点开一个崩一个。这里的站点都做过域名存活判定，
但**域名活着不等于站点能用**——spider 站依赖对方网站结构，改版即失效，这是生态本身的限制。

### 用之前要知道的三件事

1. **站多 ≠ 站能用。** 517 站的大聚合里，大量站点配的是别人 jar 的 `csp_` 扩展，
   和你的 jar 不匹配就点不开。本仓库的 165 站是每天探活筛过的，能开的比例高得多。
2. **别指望自动更新。** 这些地址是别人在维护，失效是常态，用之前先确认能打开。
3. **换回主配置很简单**：设置 → 配置地址 → 粘回第一节那个 `config_all.json` 地址即可。
